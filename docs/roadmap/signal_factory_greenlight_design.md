## Problem Statement

Upstream engineering service teams make schema changes for legitimate business
reasons but have zero visibility into downstream analytical dependencies. ML
models and marketing analytics pipelines are invisible to them — not from
negligence, but from blindness. These schema breaks have caused multi-million
dollar incidents, multiple times. Each incident follows the same expensive
manual workflow: consumer discovers the issue → data team investigates to find
the upstream culprit → multi-team remediation call → upstream service restreams
data and performs historical load → downstream confirmation. MTTD is measured
in days (consumer-driven, not automated). Remediation is expensive and recurring.

The failure mode is organizational, not technical. The producer does not know
what depends on their data. The fix is not more monitoring. It is making blast
radius legible to the producer at the moment they press deploy.

---

## Demand Evidence

- Bad schema changes from upstream services propagated and created several
  million dollar downstream impact, occurring multiple times.
- Each incident required a multi-team remediation involving the data team,
  the upstream service team, restreaming, and historical load correction.
- MTTD is currently measured in days — detection is entirely consumer-driven,
  not automated. No system catches the break before a human does.
- Incidents are recurring, indicating no systemic forcing function exists to
  stop upstream teams from repeating the behavior.

---

## Status Quo

When a schema break happens today:

1. A consumer (ML team, marketing analytics team) notices something is wrong.
2. They inform the data team.
3. The data team investigates to identify which upstream service caused it.
4. The data team brings the upstream service into a remediation call.
5. The upstream service restreams the affected data.
6. A historical load is performed to correct downstream datasets.
7. The data team confirms with downstream users that the data is clean.

This entire cycle runs on human bandwidth. No system detects, attributes, or
routes the incident. The restream + historical load is expensive compute. The
multi-team coordination overhead is significant. And the same class of incident
recurs because the upstream engineer never sees the dependency map.

---

## Target User and Narrowest Wedge

**Target user (sponsor):** Data platform or VP of Engineering leader who owns
data reliability SLAs. Success metrics: measurable MTTD/MTTR improvement with
before/after evidence, visibility into active data issues, prevention (not just
detection), and adoption progress across the organization.

**Narrowest wedge:** A single screen showing an upstream service engineer —
at the moment they open a PR with a schema change — exactly which downstream
ML models, Airflow DAGs, and marketing pipelines will be affected, with the
dollar impact from prior incidents for those specific assets. This does not
require enforcement. It requires only lineage + incident history made visible.

---

## Constraints

- 4 engineering teams, 12-month implementation roadmap
- AWS-native: MSK Kafka, EKS, Neptune, DynamoDB, Glue Schema Registry, S3, Bedrock
- Out-of-band enforcement pattern (validation never blocks data flow)
- Batch and streaming observability in scope
- No existing automated baseline for MTTD/MTTR — must establish before first ship
- Progressive Gate Enforcement Levels: G0 (visibility only) → G1 (warn) → G2 (soft-fail) → G3 (hard-fail). These are rollout stages, not validation gates. G1–G5 elsewhere (G1_RESOLUTION, G3_SCHEMA, etc.) are Policy Enforcer validation gates — a different namespace.

---

## Premises

1. **Eliminating remediation is the primary value**, not reducing MTTD.
   The expensive part of each incident is the restream + historical load cycle.
   The Certified View + Quarantine pattern — holding the consumption surface at
   the last known good version automatically — is the feature that eliminates
   this cost, not faster alerting.

2. **Producer blast-radius visibility is higher leverage than consumer alerting.**
   The problem is that upstream producers are blind to downstream dependencies.
   Showing them the blast radius before deploy prevents the incident. Alerting
   consumers after deploy only speeds up the remediation cycle.

3. **MTTD/MTTR baselines must exist before the first component ships.**
   The sponsor needs before/after metrics. Without a baseline measurement of
   current MTTD/MTTR (measured from incidents in the last 12-18 months), there
   is no "before" to compare against. Baseline collection is a Day 0 task.

4. **G0 (visibility only, no enforcement) for all datasets first.**
   Trust must be built before enforcement — even for teams that have been
   involved in prior incidents. Jumping to enforcement on day one kills
   adoption. The progressive gate sequence (G0 → G1 → G2 → G3) is the
   rollout strategy, not just an architecture feature.

## Approaches Considered

### Approach A: Blast-Radius Demo (Minimal Viable)
Build the 48-hour prototype with real incident data to greenlight the full
platform. Python + FastAPI + static JSON lineage graph. Hard-code actual dollar
figures from past incidents. No AWS, no Neptune, no Docker. The output is a
demo that answers the sponsor's question with real data.

- Effort: S (human: 2-3 days / CC: ~2 hours)
- Risk: Low
- Completeness: 3/10 — demo only, throws away code, no path to G0 monitoring

### Approach B: Lineage-First Production Path (Ideal Architecture)
Neptune Graph + Lineage Ingestor as the production wedge. First user-facing
feature is blast-radius visibility to producers before deploy. G0 observability
on all datasets. Certified View + Quarantine eliminates the restream cycle from
day one for participating datasets.

- Effort: L (human: 3-4 months / CC: ~3-4 weeks)
- Risk: Medium
- Completeness: high — full platform vision with correct component ordering per this document's premises

## Recommended Approach: A then B

**Stage 0 — Baseline (Week 0, before any code):**

Pull the last 12-18 months of incident records. Measure current MTTD/MTTR
using this protocol:

- **MTTD start:** Timestamp of the upstream schema change deploy (from deploy
  logs or Git tag). MTTD end: Timestamp of first consumer report or automated
  alert (Jira ticket creation, PagerDuty alert, or first Slack message in the
  incident channel).
- **MTTR start:** Same as MTTD end. MTTR end: Timestamp of downstream
  confirmation that data is clean (data team sign-off in Jira or Slack).
- **System of record:** Prefer Jira for formal incidents; fall back to Slack
  incident channels if Jira is incomplete.
- **Restream cost baseline:** For each incident, record: (a) compute hours for
  the restream + historical load job, (b) engineer hours across all teams on
  the remediation call and confirmation, (c) estimated dollar impact to
  downstream systems (bad ML predictions, wrong marketing spend, etc.). This
  is the "before" figure that Premise 1 claims the Certified View eliminates.
- **Owner:** Data platform lead. **Due:** Before Stage 1 demo begins.
- **Fallback:** If fewer than 3 incidents have recoverable timestamps, document
  the gap and use available partial data with explicit confidence annotations.

**Stage 1 — Demo (Days 1-3):**

Build Approach A. Use real incident datasets. Model the actual dependency graph
as a JSON file with URN-format identifiers (e.g., `urn:dp:orders:created`)
matching the canonical URN naming standard — this enables zero-friction
migration to the production Neptune graph. Nodes: Kafka topics, services, ML
model names, Airflow DAG names. Edges: "produces", "consumes",
"feature-depends-on". Run the actual upstream schema change through the
prototype. Show the blast radius and the dollar figure on a single screen.
Generate the "PR comment" screenshot showing what the bot would have posted on
the upstream service's PR.

**Stage 1 PR comment screenshot fidelity:** Produce a rendered screenshot from
a real test GitHub repository (not a Figma mockup). Create a draft PR in a
sandbox repo, post the blast-radius output as a bot comment, and screenshot
the actual GitHub UI. This is the VP money shot — it must look like a real
GitHub comment, not a wireframe.

**Stage 1 Exit Criteria:** Sponsor reviews the prototype against at least 2
historical incidents and confirms in writing that the blast-radius visualization
would have changed the upstream engineer's behavior before deploy. Written
confirmation = greenlight to proceed to Stage 2.

**Blast-radius interface decision (locked at Stage 1 exit):** Provisional
decision: PR comment bot via GitHub Actions first; developer portal integration
deferred to Stage 3. This is a provisional choice for planning — it is formally
locked after the sponsor greenlight meeting and governs Stage 2 engineering scope.
The Distribution Plan section below reflects this provisional decision; it is
subject to change at Stage 1 exit.

**Fallback:** If historical incident records are not retrievable within 48
hours, construct a representative synthetic incident using known schema change
patterns and publicly documented dollar-impact proxies. Flag the demo as using
representative figures.

**Stage 2 — Production Wedge (Months 1-3):**

**Rationale for component ordering:** This stage starts with C-08 (Lineage
Ingestor) + C-06 (Neptune Graph) rather than C-01 (Policy Enforcer) as
specified in the PRD's Phase 1. The justification: producer blast-radius
visibility (Premise 2) requires a populated lineage graph before it can be
delivered. The Policy Enforcer generates evidence, but without the lineage
graph, evidence records have no blast-radius context attached. Starting with
Neptune+Lineage means the first user-facing feature (blast-radius visibility to
producers) is deliverable in Month 2, not Month 6.

**Cross-team dependency:** Team 1 (Platform Core) must deliver C-03 Evidence
Bus batch schema extensions by end of Month 2 (per PRD Phase 1 plan). This
unblocks: (a) live evidence feed into Neptune, replacing the static JSON seed;
(b) Stage 3 G0 metric collection. If C-03 slips past Month 2, Stage 3 G0
rollout and Stage 2 live blast-radius both slip by the same amount. Team 2
(Signal Processing) owns C-08 and C-06; they cannot unblock themselves on
this dependency. Escalation path: platform lead flags to eng management if
C-03 is not on track by end of Month 1.

**C-08 bridge state:** Neptune will be seeded from the static JSON lineage
graph (validated during Stage 1) via a one-time import script. This is a
Stage 1 deliverable, not Stage 2. Bridge period is expected to last until
C-03 batch schema extensions are live (Month 2). During the bridge period:
(a) the import script owner (Team 2) must refresh the static seed weekly from
any schema changes discovered manually; (b) the blast-radius screen must
display a "Lineage last updated: {date}" watermark so producers know the
data age; (c) Neptune graph staleness beyond 7 days is an incident requiring
an unplanned static seed refresh. Bridge state retirement: when the first
live evidence batch runs end-to-end through C-03 → C-08 → C-06 successfully.

**Stage 2 Exit Criteria:** C-08 + C-06 in production with live evidence feed
active (bridge state retired). At least one Tier-1 blast-radius notification
delivered to a producer via the GitHub Actions bot (real deployment, not demo).

**Milestone — First Restream Elimination (target: end of Month 3):**
One Tier-1 batch pipeline operating with Certified View + Quarantine active,
with zero restream events in a 30-day window. This is the ROI event that
converts the sponsor greenlight into continued investment. Owners: Team 1
(Policy Enforcer, Evidence Bus) + Team 2 (Signal Engines, Neptune).

**Stage 3 — G0 Observability Rollout (Months 2-4):**

Stage 3 runs in parallel with Stage 2 and is independent of the Stage 2 First
Restream Elimination milestone. The two stages share one dependency: C-03
Evidence Bus batch schema extensions (Month 2, Team 1). Stage 3 instrumentation
PRs can be drafted and reviewed in Month 2; metric collection against the
Stage 0 baseline starts in the first full week of live evidence data after C-03
is deployed. Stage 3 does not block on Stage 2 exit.

Instrument datasets at G0 (visibility-only enforcement level; no alerts, no
blocks) across all teams. Build the adoption progress dashboard the sponsor
needs. Do not advance any dataset past G0 until it has been visible for at
least one sprint.

**Stage 3 Exit Criteria:** 80% of Tier-1 + Tier-2 datasets at G0 or above.
Adoption dashboard live and reviewed by sponsor. At least one full sprint of
MTTD/MTTR data collected against the Stage 0 baseline.

**Stage 4 — Progressive Enforcement (Months 4+):**

Advance Tier-1 incident datasets from G0 (visibility only) → G1 (warn) → G2
(soft-fail) based on team readiness and measured baseline improvement. G3
(hard-fail in production) only for Tier-1 datasets with demonstrated team
adoption and at least one MTTD/MTTR improvement metric.

**Stage 4 Exit Criteria:** At least 3 Tier-1 datasets at G2 (soft-fail) or
above. MTTD < 30 minutes and MTTR < 4 hours demonstrated on at least one
live incident. Fallback if no qualifying incident occurs before the 6-month
sponsor review: inject a synthetic schema-break event against a staging
Tier-1 pipeline, run the full detection and Certified View response, and
present the measured MTTD/MTTR from the synthetic incident with explicit
labelling. Synthetic incident results satisfy the exit gate only if the
sponsor accepts them in writing as equivalent evidence.

## Open Questions

1. **Incident records:** Are the past schema-change incidents documented
   anywhere (incident management system, Slack archives, Jira)? The baseline
   measurement and the demo both depend on retrieving real incident timelines
   and dollar figures.

2. **Lineage ownership:** Who owns the lineage spec — the SCA team (External
   Lineage Service) or the data platform team? The Lineage Ingestor (C-08)
   depends on this boundary being clear before the first sprint.

3. **Schema Registry coverage:** Are all upstream services currently
   registering schemas in Glue Schema Registry? If not, G3 Schema gate
   enforcement cannot be applied even to Tier-1 datasets until producers
   are onboarded.

4. **Adoption metric definition:** What counts as "adopted"? Dataset
   registered + G0 enabled? G1 passed? The sponsor's adoption progress
   dashboard needs a clear definition before Month 1.

5. **Blast-radius interface:** Where does the producer see the blast radius?
   PR comment bot (GitHub Actions), pre-deploy hook, internal developer
   portal, or all three? This determines which CI/CD integrations are in scope
   for Phase 2.
