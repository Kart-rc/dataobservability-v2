## Problem Statement

The Signal Factory platform needs leadership to fund it across a 12-month roadmap
before most of its value is visible. Without a credible, non-vanity visibility
layer from Week 1, the program risks being defunded during the gap between "we
started building" and "we caught a real incident." Leadership visibility must be
a first-class operating layer — not a reporting afterthought — that gives
executives, program managers, and engineers different but coherent views of the
same underlying evidence.

The specific risks this design addresses:
1. Leadership sees nothing for 3 months, gets nervous, scopes the program down.
2. Vanity metrics (PR count, SDK installs, dashboard count) creep in and erode
   credibility when they don't translate to detected incidents.
3. The platform team owns the leadership artifact, turns it into a technical
   status report, and loses its executive audience.
4. All six scorecard dimensions launch simultaneously on infrastructure that
   doesn't yet support most of them, producing misleading zeros and "N/A" rows.

---

## Premises

1. **Phased scorecard.** Leadership does not need all six dimensions from day one.
   Launching a dimension before the platform can populate it produces "N/A" rows
   that undermine credibility. Dimensions unlock only when supporting evidence
   exists.

2. **Vanity metric replacement.** "Don't reward PR count, SDK presence, or
   dashboard count" is correct but requires an explicit early alternative.
   Before MTTD/MTTR data exists, the visible progress signal must be
   Blast Radius Coverage % (Tier-1 datasets in Lane A / total known Tier-1)
   and Time-to-First-Signal (minutes from evidence event to alert or clean
   confirmation). These are real, pipeline-proving metrics available from
   Day 1 of Lane A enrollment.

3. **Lane A vs. Lane B vs. Autopilot.** Three distinct mechanisms:
   - Lane A: zero-change, out-of-band enrollment (available Stage 2, Day 1).
   - Manual Policy Bundles: YAML config authored by platform team for Tier-1
     datasets (available Stage 2, Day 1 — no producer code change required,
     no Autopilot dependency).
   - Lane B / Autopilot: Scout + Author/Review agents generating producer-side
     PRs (Phase 4 capability, Months 5-8). Not in scope for this operating model.

4. **Three separate artifacts, three owners.** One combined dashboard loses its
   audience because executive, program, and platform health cadences and tools
   diverge. Each artifact has exactly one owner, one primary audience, and one
   update cadence.

## Scorecard Dimensions — Phased Unlock

Dimensions unlock as the platform reaches the stage that can support them.
Launching a dimension before its stage is live produces misleading data.

**Stage number note:** Stage 0-4 in this document follow the greenlight design's
scheme, not the PRD's Phase 1-4 scheme. PRD Phase 1 (Foundation, M1-M2) runs
concurrently with Stage 0-1. See `docs/roadmap/signal_factory_greenlight_design.md`
for the full mapping.

| Dimension | Unlocks at | What it measures |
|-----------|-----------|-----------------|
| **Coverage** | Stage 2 Week 1 | Blast Radius Coverage %, trust-tier mix |
| **Operations (proxy)** | Stage 2 Week 1 | Time-to-First-Signal (MTTD precursor) |
| **Adoption** | Stage 3, Week 1 of live evidence (Month 2-3, gated on C-03 Evidence Bus delivery) | Time to baseline, G0/G1/G2/G3 distribution, rollback rate |
| **Operations (real)** | Stage 3, Week 1 of live evidence (Month 2-3, gated on C-03 Evidence Bus delivery) | MTTD delta, MTTR delta vs. Stage 0 baseline |
| **Business Impact** | Stage 3 (first prevented incident or restream elimination) | Sev cost avoided, hours saved, Tier-1 assets protected |
| **Prevention** | Stage 4 (G2+ enforcement active) | Prevented schema issues, prevented stale-data exposures |
| **RCA Quality** | Stage 4 (Neptune + RCA Copilot live) | % incidents with deterministic or high-confidence causal explanation |

**Anti-vanity rule:** The scorecard NEVER reports PR count, SDK installs, or
dashboard count. If a metric cannot be traced to a closed Tier-1 gap, a reduced
MTTD/MTTR, or a prevented incident, it does not appear in the leadership artifact.

## The Three Artifacts

### Artifact 1 — Executive Scorecard
**Owner:** Program Manager (not the engineering lead)
**Audience:** VP, Director, executives funding the program
**Cadence:** Weekly, delivered Monday 8am before leadership standup
**Format:** One slide. Two numbers in Stage 2, expanding to four by Stage 3.
**Rule:** Thresholds set in advance and locked. No retroactive adjustment.

**Stage 2 content (Weeks 1-12):**

| Metric | Definition | Source | Target |
|--------|-----------|--------|--------|
| Blast Radius Coverage % | Tier-1 datasets enrolled in Lane A / total known Tier-1 datasets | DynamoDB DatasetRegistry | 80% by end of Month 2 |
| Time-to-First-Signal | Median minutes: first evidence event emitted → alert generated or clean confirmed | Evidence Bus + Alerting Engine | < 5 min for enrolled datasets |

Include one static section: **"What would have happened"** — a worked example
using the most expensive prior schema-change incident. Update this section only
when a real detection event supersedes the synthetic example.

PM-buildable template (no engineer required):
1. One-sentence incident summary (dataset affected, date, root cause)
2. Blast-radius count (how many downstream ML models/dashboards affected)
3. Actual restream cost from Stage 0 baseline (compute hours + engineer hours + dollar impact)
4. What the platform would have emitted: G3_SCHEMA alert within Time-to-First-Signal threshold, Certified View held at last good version, quarantine triggered — no restream required
5. Estimated time saved vs. actual MTTR from the incident

The Stage 1 demo's PR comment screenshot (blast-radius visualization) is the
canonical visual for this section until the first real detection event replaces it.

**Stage 3 additions (Month 2+, when live evidence exists):**

| Metric | Definition | Source | Target |
|--------|-----------|--------|--------|
| MTTD delta | Current median MTTD vs. Stage 0 baseline | Evidence Bus timestamps | < 30 min (from days) |
| MTTR delta | Current median MTTR vs. Stage 0 baseline | Incident resolution timestamps | < 4 hours (from multi-day) |

**Stage 4 additions (when enforcement is active):**

| Metric | Definition | Source | Target |
|--------|-----------|--------|--------|
| Prevented incidents | Incidents caught and quarantined before consumer impact | Certified View + Quarantine events | Rising over time |
| Sev cost avoided | Estimated dollar value of prevented restream cycles | Incident cost model from Stage 0 baseline | Rising over time |

### Artifact 2 — Program Dashboard
**Owner:** Platform Program Manager
**Audience:** Engineering team leads, data platform leadership
**Cadence:** Biweekly, reviewed in platform sync
**Format:** Stage 2 — static Notion/Confluence page with manual weekly updates
(DynamoDB DatasetRegistry not yet live). Stage 3+ — internal web app with live
data queries against DynamoDB DatasetRegistry and Evidence Bus.

**Content (all stages):**

**Onboarding progress:**
| Column | Definition |
|--------|-----------|
| Datasets at G0 | Enrolled, evidence flowing, visibility only |
| Datasets at G1 | G0 + missing contracts / weak trace anchors flagged |
| Datasets at G2 | Lower-env soft enforcement + prod alerting active |
| Datasets at G3 | Hard-fail in production for mature Tier-1 controls |
| Tier-1 gap backlog | Tier-1 datasets not yet enrolled — explicit, dated, owned |

**Progress metrics:**
- Time to baseline per new dataset (days from enrollment to first evidence)
- PR merge SLA for manual Policy Bundle authoring (target: < 5 business days)
- Rollback / revert rate for Policy Bundle deployments (target: < 5%)
- Producers onboarded by domain (not by language or PR count)

**Conformance check:** Every Tier-1 dataset must answer yes to:
- Asset discovered and owned?
- Dataset URN and resolution known?
- Evidence flowing?
- Freshness + volume + contract-lite signals active?
- Trust tier assigned?
- Business-value baseline recorded?
- Tier-1 residual gaps tracked explicitly with owner and due date? (Autopilot-eligible in Phase 4 — not currently operational)

---

### Artifact 3 — Platform Health View
**Owner:** Engineering Lead (Team 1 — Platform Core)
**Audience:** On-call engineers, platform team
**Cadence:** Continuous (live dashboard); reviewed in weekly eng sync
**Format:** Grafana or equivalent, with PagerDuty integration for breaches

**Metrics:**

| Metric | SLO Target | Alert threshold |
|--------|-----------|----------------|
| Evidence latency P99 | < 2 seconds | > 5 seconds |
| Evidence completeness | > 99% | < 95% |
| Enforcer lag | < 2 seconds | > 10 seconds |
| Evidence Bus lag | < 1 second | > 5 seconds |
| Signal freshness | < 5 minutes | > 10 minutes |
| Neptune write health | > 99.9% | Any write failure |
| DynamoDB write health | > 99.9% | Any write failure |

**Critical rule:** Gaps in evidence must be classified as:
- **Producer failure** (upstream service down, not emitting) — reported to producer team
- **Platform failure** (Evidence Bus, Enforcer, or Schema Registry down) — escalated to Team 1

Platform failures must never be counted as producer non-compliance in Artifact 1 or 2.

## Bootstrap Path for New Applications

When a new application or dataset is registered, onboarding follows this sequence:

1. **Trigger** — repo registration, service registration, or explicit platform request
2. **Discovery** — scan repo, config, ownership registry, known sinks/sources
3. **Pattern match** — map to known signal pattern; estimate expected evidence types
4. **Tier assignment** — assign dataset tier (TIER_1/2/3) based on downstream blast radius and incident history
5. **Lane A enrollment** — register in DatasetRegistry (`dataset.yaml` with URN-format ID), attach out-of-band signal generation, create baseline G0 dashboards and alerts
6. **Readiness score** — compute trust tier across: trace anchor coverage, identity confidence, deploy correlation coverage, policy completeness
7. **Tier-1 gap check** — if Tier-1 and readiness score is below acceptable threshold, platform team authors manual Policy Bundle (YAML) and routes through approval. This is Day 1 work, not Phase 4 work.
8. **Record business-value baseline** — attach Stage 0 incident history for this asset (if any) to enable future "cost avoided" calculation
9. **Conformance ladder entry** — asset enters at G0; advancement gated on evidence quality and team readiness

**Definition of "done" for a new application:**
- [ ] Asset inventory exists in DatasetRegistry
- [ ] Ownership and tier assigned
- [ ] Dataset URN and resolution confirmed
- [ ] Evidence flowing (at least freshness + volume)
- [ ] Trust tier assigned (Inferred / Platform-attested / Producer-attested)
- [ ] Business-value baseline recorded
- [ ] For Tier-1: Policy Bundle authored and deployed; gaps on explicit backlog

## Trust Progression Model

| Trust Level | How achieved | What it enables |
|-------------|-------------|----------------|
| **Inferred** | Repo/config/catalog inference, no producer changes | G0 visibility, basic coverage metrics |
| **Platform-attested** | Deploy events, Delta history, scheduler metadata, Kafka principal, traces, Evidence Bus | G1 warn, strong blast-radius attribution, Time-to-First-Signal reliability |
| **Producer-attested** | Contracts, `event_time`/`processing_time`, producer identity field, semantic URN markers | G2/G3 enforcement, prevention metrics, deterministic RCA |

For Tier-1 assets: **Platform-attested or Producer-attested evidence is required**
for high-confidence RCA and prevention claims. Inferred-only Tier-1 evidence must
be flagged as low-confidence in Artifact 1 until promoted.

## Open Questions

1. **Who is the Program Manager?** Artifact 1 and 2 both require a named PM owner.
   If no PM is assigned before Stage 2 Week 1, engineering will default to owning
   the executive artifact — and it will become a technical status report.

2. **What is the Tier-1 dataset inventory?** Bootstrap Step 4 requires a known list
   of Tier-1 assets. If that inventory doesn't exist, Blast Radius Coverage % cannot
   be computed. Creating this inventory is a Stage 0 task alongside the MTTD/MTTR
   baseline.

3. **What is the incident cost model?** Artifact 1's "Sev cost avoided" requires a
   per-incident dollar model from Stage 0. If only 1-2 incidents have cost estimates,
   the model must be clearly labelled as an extrapolation, not a precise figure.

4. **What tooling hosts Artifact 2?** The Program Dashboard requires live queries
   against DynamoDB DatasetRegistry and Evidence Bus. This assumes Stage 3 infrastructure
   is live. In Stage 2, a static Notion/Confluence page with manual weekly updates
   is the fallback.

## Dependencies

- **Stage 0 Tier-1 dataset inventory** — required before Blast Radius Coverage % is
  computable. Owner: data platform lead. Due: same as MTTD/MTTR baseline.
- **PM assignment** — required before Stage 2 Week 1. Owner: engineering manager.
- **DynamoDB DatasetRegistry** — Artifact 2 live queries depend on this being live
  (Stage 2). Fallback: manual Notion page.
- **Evidence Bus live** — Time-to-First-Signal requires the Evidence Bus to be
  emitting events. This is a Stage 2 dependency; see greenlight design Stage 2
  cross-team dependency note.
